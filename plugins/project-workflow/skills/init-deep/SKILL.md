# init-deep

为目标仓库建立耐久、简洁、可验证的 `AGENTS.md` 指导层级。始终把仓库根目录的 `AGENTS.md` 作为主要产物；只在子树确有不同操作要求时保留或创建更近的文件。

完成结果应满足以下条件：

- 未来的编码代理能找到重要入口、正确的改动位置、项目特有约束和权威验证命令。
- 根文件承担仓库范围的共同指导，子文件只补充适用于本地的差异，不复述父级内容。
- 所有写入内容都有仓库证据支持；不确定事项被明确标记或省略。
- 每个变更文件及其继承关系都经过检查，报告只声称实际执行过的验证。

## 权限与停止条件

先确认目标仓库、仓库根目录和用户授权的可写范围。把初始化、修复或刷新请求视为允许进行范围内的本地读取、编辑和非破坏性验证；持续完成这些安全工作，无须逐步询问。

在外部写入、删除或覆盖难以恢复的内容、执行明显昂贵的操作，或扩大目标范围前取得确认。仅当缺失决定会实质改变范围、风险或产物时提问。

若根目录 `AGENTS.md` 不在可写范围内，停止写入，不要用仅创建子文件来替代；请求获得完成根产物所需的最小权限。若关键证据不可读取、仓库边界无法确定，或必要验证无法安全运行，说明准确阻碍和最小下一步。

## 查明有效指导与仓库边界

确定实际项目根目录；在多仓库工作区、子模块或嵌套版本库中，不要把工作区目录默认当作仓库根目录。记录用户指定范围与检测到的边界是否一致。

读取所有可能约束目标仓库根目录及候选子树的现有指导文件，包括有效的 `AGENTS.override.md`、`AGENTS.md`，以及配置中声明的回退文件名。沿每个候选子树的继承路径检查实际生效顺序，并注意：

- 同一目录中只会采用优先级最高的非空指导文件。
- 从项目根目录到工作目录的文件按路径顺序合并，越近的指导优先。
- 空文件不会生效，合并后的指导还可能受项目文档字节上限约束。

把现有规则视为需要保留的项目证据。保留有意且仍然准确的约束；只有在用户要求或仓库证据直接反驳时才修正。遇到覆盖文件遮蔽 `AGENTS.md`、父子规则互相冲突、回退文件仍在生效或来源不明的规则时，先查清影响再编辑，不要静默假定。

## 建立证据账本

收集足以支持最终指导的证据，并在工作记录中把每项结论关联到具体来源。至少查明有证据可得的以下事项：

- 仓库或子树负责什么，主要边界与入口在哪里；
- 常见改动应落在哪些区域，模块、包、服务或应用如何分工；
- 构建、开发、格式化、静态检查和测试命令的权威来源；
- 生成代码、供应商代码、迁移、模式、发布配置等不可随意修改或需特殊流程的区域；
- 本地安全、兼容性、所有权或高风险约束。

优先用可用的结构化代码工具查找符号、调用关系、模块边界和入口；用文件系统搜索查找配置、清单、任务运行器、CI 定义、文档和字面规则。通过清单、锁文件、工作区配置、脚本定义、测试配置和 CI 用法交叉核对命令，不要只凭目录名或常见生态惯例推断。

让证据账本保留：结论、来源路径或命令、适用范围，以及会影响指导的疑点。无需把账本写入仓库。若搜索结果为空、残缺或异常狭窄，换用一个小而有意义的来源或工具复查后，才判断证据不存在。对仍然缺失的材料标记不确定性；不要补写猜测。

可并行读取彼此独立的证据源，但只在确实减少等待时间时这样做。让同一执行者统一完成层级决策、内容合成和最终验证，避免因并行草稿产生重复或矛盾。进度更新只用于重要阶段变化、风险变化、长时间等待或需要用户操作时。

## 决定指导层级

先确定根文件应承载的仓库共同规则，再评估候选子树。采用定性的边际价值判断，不以数值规则、目录数量限制或预设层级限制代替证据。

仅当以下判断同时成立时，为子树创建或保留嵌套 `AGENTS.md`：

- 有已验证的本地命令、约束、责任边界或风险，确实不同于仓库共同规则；
- 把这些内容放在根文件会误导其他区域，或给根指导增加明显噪声；
- 子文件可以只写局部增量，仍对未来在该子树工作的代理有独立价值。

若差异只是名称即可看出的事实、父级规则的重复、短期目录清单或未经验证的猜测，不创建子文件。重新评估每个现有子文件；若它已无实质局部价值，提出合并或移除方案。移除文件前按破坏性操作边界取得确认，不要先删除整套指导再重建。

## 撰写和更新文件

先写或更新仓库根目录 `AGENTS.md`，确认其能够独立承载仓库范围的指导后，再处理子文件。对现有文件做聚焦修改，保留仍然有效的内容和用户措辞；不要进行无证据支持的大范围改写。

按仓库需要选择短标题，不强制统一章节模板。只写有证据、能改变代理行为的内容，例如：

- 仓库或本地子树的职责与关键入口；
- 常见改动的正确归属位置；
- 项目特有的必须遵守或禁止事项；
- 来源明确的开发与验证命令；
- 不直观的生成边界、所有权接缝和高风险区域。

根文件写共同规则，子文件只写更窄范围的补充或更具体的替代命令。不要在子文件复制父级说明；必要时用一句话界定局部范围，然后直接给出增量。

保持内容简洁、可执行、跨时间稳定。省略空类别、通用软件建议、仅凭名称即可知道的事实、时间戳、提交标识、容易过期的完整目录盘点，以及未被仓库证据证实的命令。若重要不确定性会影响操作，明确写成待确认条件，而不是伪装成事实。

## 验证最终结果

写入后逐一重新读取所有变更的指导文件，并验证：

- 文件位于预期路径，根文件确实存在且为主要产物；
- 路径、入口和命令与证据一致；
- 从根到各子树的继承顺序清楚，没有冲突、失效覆盖或不必要重复；
- 内容足够短且关键指导不会因合并大小限制而被截断；
- 每个子文件仍通过局部价值判断，不值得存在的子文件已被列为需确认的处理项；
- 未丢失现有的有意规则，也没有写入临时事实或通用填充。

运行与改动最相关且成本最低的非破坏性命令检查。优先验证文档中实际提到的命令或其定义；若完整测试明显昂贵，选择能证明命令可解析、配置可加载或目标可枚举的较小检查，并如实说明未运行的部分。不得把未执行的检查写成成功。

发现证据矛盾、重复或无效子文件时，继续在授权范围内修正并重新验证。只在根产物存在、层级决策有证据、全部变更文件已复查且可执行的相关检查已完成或明确受阻后结束。

## 交付报告

以结果开头，简要列出：

- 创建和更新的 `AGENTS.md` 路径；
- 支撑关键结论的仓库证据来源；
- 实际执行的验证及结果；
- 有意义的省略项、未验证事项和阻碍；
- 若仍需用户操作，给出最小下一步。

先保留结果、证据、重要限制和下一步，再删减次要过程描述与重复内容。
